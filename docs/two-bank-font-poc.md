# 정적 2뱅크 글꼴 PoC — FONT-TWO-BANK-POC-001

## 현재 판정

`FONT-TWO-BANK-POC-001`은 **bank-aware ABI runtime PASS**, bank 1 상주지는
`FONT-TWO-BANK-VRAM-002` 세션 005까지의 런타임 감사로 **`(448,0)`–`(512,256)`,
tpage `0x07`로 확정**됐다. 이어서 `FONT-TWO-BANK-POC-002`가 이 페이지 기준의
**배포 가능한 저장·업로드 경로와 타이틀 시각 E2E를 런타임 PASS**로 닫았다
(아래 "E2E PoC — FONT-TWO-BANK-POC-002" 절). 남은 것은 PoC 빌드에서의 메뉴·게임
텍스트 HITL 회귀 확인과 전체 corpus atlas 제작이다.

원본 decoder의 반환값을 `bit 8 = bank`, `bits 7..0 = cell`로 확장했다. 기존 공용
primitive builder는 5개 명령만 제자리 교체해 bank 0이면 `tpage=0x1F`, bank 1이면
`tpage=0x1E`를 기록하고, 낮은 8비트 셀 번호의 기존 U/V 계산은 그대로 유지한다.
범용 renderer·단일 글리프 renderer·움직이는 타이틀 builder가 모두 이 공용 builder를
호출하므로 별도 호출자 ABI를 추가하지 않았다.

DuckStation 새 부팅 GDB 추적에서 `한` 토큰의 decoder 반환값 `0x1DE`가
`0x80042F84`에 도달했고, 생성 중인 `POLY_FT4`가 `U=0xE0`, `V=0xD0`,
`tpage=0x001E`를 갖는 것을 확인했다. 따라서 **decoder → bank bit → 공용 builder →
bank별 tpage/UV** 전달은 런타임 PASS다.

PoC용 bank 1은 ENIX splash TIM의 하단 배경 셀 `DE`·`DF`를 임시로 공유한다. 이 페이지가
타이틀 뒤의 모든 장면에서도 보존된다는 증거는 없으므로 최종 atlas 저장 위치나 전역
상주 설계로 승인하지 않는다. 창 캡처에서는 타이틀 진입과 움직이는 원문을 확인했지만
`한글` 픽셀을 독립된 시각 PASS로 판정할 만큼 명확한 전체 화면 표본은 아직 없다.

## 구현 계약

| 항목 | 값 |
| --- | --- |
| bank 0 | cell `00`–`FF`, tpage `0x1F`, VRAM `(960,256)` |
| bank 1 PoC | cell `DE`·`DF`, tpage `0x1E`, VRAM `(896,256)` |
| `한` 토큰 | `81 47` → decoder `0x1DE` |
| `글` 토큰 | `81 68` → decoder `0x1DF` |
| builder 패치 | runtime `0x80042F84`, ARA `0x6CF84`, 20바이트 제자리 교체 |
| 타이틀 표본 | HAGECHO `0x1A064`의 첫 두 토큰 |

builder의 패치 명령은 다음과 같다.

```asm
srl  $v0, $s1, 8
xori $v0, $v0, 0x1f
sh   $v0, 0x16($t0)
sll  $v0, $s1, 4
sb   $v0, 0x0c($t0)
```

bank 0의 기존 decoder 값은 8비트이므로 첫 두 명령의 결과가 계속 `0x1F`다. bank 1은
bit 8이 1이므로 `0x1E`가 된다. `sb`는 낮은 8비트만 기록하므로 cell의 하위 nibble U
계산은 bank bit와 충돌하지 않는다. V 계산도 기존 `andi $v0,$s1,0xF0`을 유지한다.

## 다음 VRAM 게이트

`FONT-TWO-BANK-VRAM-001`은 전체 TIM 121개의 image/CLUT 사각형을 64×256-word tpage
후보와 대조했다. `(704,256)`–`(768,512)`, tpage `0x1B`는 정적 TIM 겹침이 0인 우선
프로브다. 그러나 TIM 목록은 framebuffer, GPU clear, 직접 CPU→VRAM 전송과 비TIM
동적 자산을 포함하지 않으므로 **안전 확정이 아니라 런타임 감사 후보**다.

## 런타임 점유 감사 — FONT-TWO-BANK-VRAM-002

이 빌드의 DuckStation은 GPU 디버그 로그 문자열이 없고(과거 로그 캡처도 업로드 0건),
GDB 서버는 레지스터 쓰기(`G`/`P`/`p`)를 지원하지 않는다(라이브 확인, 빈 응답).
따라서 감사는 **레지스터·pc 쓰기가 없는 in-line pc hijack** 방식으로 구현했다:
멈춘 지점 `F`의 2개 명령을 `j 0x80017000; nop`으로 치환하고, 스크래치의 MIPS
스텁이 t-레지스터 8개와 SR을 스스로 저장→인터럽트 비활성→GPU 유휴 대기→GP1(04h)
DMA 차단→GP0 `C0h`(VRAM→CPU)로 후보 사각형 64×256 word를 RAM 버퍼에 판독→DMA
방향·SR·레지스터 복원→원본 2개 명령을 트램펄린에서 실행→`F+8` 복귀(Z0 정지)한다.
프로브마다 패치와 스크래치를 바이트 복원하며, 유일한 비복원 부작용은 GPU read
cursor 소비다. `F` 선택은 `F-4`/`F`/`F+4` 3개 명령이 모두 제어 흐름이 아닐 때만
허용하고, 아니면 단계 실행으로 이동한다(도구: `capture_vram_occupancy.py`).

| 세션 | 스케줄 | 프로브 | 결과 |
| --- | --- | --- | --- |
| 001 | 20–240초 13회, 무인 | 성공 10, 히잭 지점 없음 3 | 사각형 SHA 전부 동일, 전체 0x0000 |
| 002 | 255–600초 14회, 무인 | 성공 14 | 사각형 SHA 전부 동일, 전체 0x0000 |

### 판정: `(704,256)`–`(768,512)` 후보 탈락

판독 픽셀 렌더(`work/graphics/vram_occupancy_003/`)에서 이 페이지의 실제 용도가
확인됐다: **Options 화면에서는 메뉴 문자열(デモンストレーション·スタッフ·
データボリューム 등)이 동적으로 렌더된 글리프 타일**로, 게임플레이 중에는 동적
스프라이트 타일로 채워진다. 즉 이 페이지는 `TEXT-READER-AUDIT-001`에서 확인한
동적 텍스트 decoder·atlas builder 경로의 **런타임 동적 atlas/업로드 캐시 영역**이다.
정적 TIM 겹침 0은 애초에 이 영역이 TIM이 아닌 동적 업로드 전용이기 때문이었다.
따라서 bank 1 상주지로는 탈락이며, 정적 TIM 겹침 0인 다른 후보들도 같은 이유로
의심해야 하므로 **동일한 HITL 게임플레이 세션에서 런타임 감사를 통과해야만**
후보로 인정한다.

부수 확인: 무인 구간 판정(0 쓰기)은 세션 003의 30초 표본(메뉴, 여전히 0)과
일관된다. 프로브의 순간 표본 특성상 프로브 사이에 썼다가 되돌리는 쓰기는 보이지
않는다는 한계는 판정 JSON의 `limits`에 기록했다.

## E2E PoC — FONT-TWO-BANK-POC-002

`FONT-TWO-BANK-POC-002`는 확정된 `(448,0)` 페이지로 세 가지를 배포 가능한 형태로
증명했다. 빌드 스크립트는 `workspace/scripts/build_two_bank_poc_002.py`, 설정은
`workspace/config/font_two_bank_poc_002.json`, 판정은
`work/analysis/font_two_bank_poc_002_{build,runtime_review}.json`이 소유한다.

### 1. bank 1 업로드 경로: block 0 자산 디렉터리 이전

block 0 헤더 `+0x8`은 런타임 자산 디렉터리 포인터(`0x80145DB8`)다. 디렉터리는
`[태그, 포인터]` 8바이트 엔트리 목록으로 태그 `0xFFFF0001`=TIM 업로드 9개,
`0x001005xx` 2개, 종결자 `0xFFFF0000`이며 원본 위치에는 추가 여유가 없다.
PoC는 디렉터리를 block 0 꼬리 슬랙(0x4C1F8)으로 **이전 복사**하고 TIM 엔트리
1개를 원본 순서 뒤에 추가한 뒤 헤더 포인터를 `0x80177ED8`로 바꿨다. 추가 엔트리는
슬랙의 미니 TIM(0x4C260, 544바이트)을 가리키며, 이 TIM은 글꼴 CLUT 블록의
바이트 동일 재업로드와 셀 `DE`·`DF` 이미지(`(504,208)` 8×16 word)로 구성된다.
런타임 판독(`vram_occupancy_poc2` 프로브 3회)에서 `(504,208,8,16)`이 미니 TIM
payload와 **바이트 일치** — 로더가 이전된 디렉터리를 그대로 소비함이 증명됐다.

### 2. 확장 builder 패치: tpage `0x07` 유도

bank0 `0x1F`↔bank1 `0x07`은 XOR 마스크 `0x18`(2비트)이라 기존 5명령 패치로는
부족하다. PoC-002는 builder의 tpage/U/V 계산 창 전체(`0x80042F84`–`0x80042FEC`,
27명령 108바이트)를 제자리 재작성했다: `srl v0,s1,8; negu v0,v0; andi v0,0x18;
xori v0,0x1f`로 tpage를 만들고, U/V와 4꼭짓점 복사 20명령을 레지스터 유지 방식
18명령+nop 9개로 압축했다. `$v1`은 해당 창에서 사멸 레지스터임을 확인했다
(이후 첫 접근이 `lw $v1, 0x38($sp)` 쓰기). Keystone→Capstone 왕복 검증 PASS.
bank 0 경로의 tpage/U/V 바이트 의미는 원본과 동일하며 타이틀·어트랙트의 기존
일문 텍스트 렌더에 회귀가 없다.

### 3. Room No.703 글리프와 흔들림 플레인

원본 atlas는 셀당 4bpp 니블의 **비트플레인 4장**에 지터가 다른 1비트 글리프를
저장하고 팔레트 0–3(흰색)/4–7(검정 그림자)이 플레인을 선택해 낙서풍 흔들림을
만든다. PoC는 `Font/Room No.703.ttf` 16px 렌더를 순환 오프셋

### bank 1 payload 저장 설계(후보 확정, 빌드 전 사람 QA 1건)

bank 0은 기존 글꼴 TIM(33KB)을 동일 크기로 교체하면 되고, bank 1은 190셀
(445-255)이 필요하다(256×192px 4bpp ≈ 24.6KB + TIM 헤더). block 0 슬랙은
1,552바이트라 부족하므로 **block 0 내부 재배치**로 확보한다:

- 후보: TIM idx0 타이틀 배경 `(384,256)` 256×240 **8bpp(61,984B)를 16색
  4bpp(30,992B)로 변환**해 같은 슬롯 앞부분에 두고, 뒤따르는 ~31KB 여유에
  bank 1 atlas TIM을 넣는다. 디렉터리는 이미 이전·재작성하므로 포인터 갱신은
  자유롭다. 다른 TIM은 이동하지 않는다.
- 검증·승인: 사용 색 36개를 역할 기반 수동 선별한 16색 팔레트(RMSE 6.92,
  포인트 색 전부 보존, 토끼 몸통만 미세 연화)를 사용자가 **2026-08-06 승인**했다.
  팔레트는 `workspace/config/titlebg_16c_palette.json`, 비교 근거는
  `work/graphics/font_two_bank_poc_002/titlebg_approval.png`가 소유한다.
- 기각: idx6 로고 TIM은 사용 색 168개로 16색 변환 손실이 크다.

### 컷신 정체 규명과 상주 모델 수정 — FONT-TWO-BANK-VRAM-003

컷신은 디스크의 **STR 동영상 7편**이다: `OPEN.STR`(오프닝), `GOOD/BAD.STR`,
`NE_A~D.STR`(엔딩 6종). 전 파일의 프레임 헤더가 **320×240**으로 정적 확인됐다.
캐릭터별 사망 컷신이 모두 같았던 이유도 같은 파일 재생이기 때문이다. 엔딩 6편은
어트랙트 오프닝과 같은 재생 경로를 쓰므로, **어트랙트 동영상 관측으로 엔딩까지
같은 근거로 판정**된다(치트로 엔딩까지 진행할 필요 없음).

무인 어트랙트 세션(`007attract`, 8초 간격)에서 동영상 재생 중 `(448,0)`이
초반 32워드×240행, 후반 **페이지 전체(63–64워드)**까지 덮이는 것을 확인했다.
`(512,256)`도 별도 무인 세션(`008attract`, 72표본)에서 256셀 중 **165셀이 오염**
됐다. 즉 **영구히 비어 있는 페이지는 없다.**

그러나 결정적으로, 동영상이 끝나면 `(448,0)`은 **PoC 기준 해시로 바이트 단위
복귀**한다 — 이전된 자산 디렉터리가 다음 장면 로드에서 미니 TIM을 재업로드하기
때문이다. 따라서 올바른 상주 조건은 "절대 안 쓰이는 페이지"가 아니라
**"한국어 텍스트가 화면에 있는 동안 안 쓰이고, 텍스트가 돌아오기 전에 복원되는
페이지"**다. 전체 화면 동영상 재생 중에는 게임 텍스트가 그려지지 않는다.

`(448,0)`의 대화형 플레이 근거: 세션 005 59표본, 006b 36표본, poc2reg 42/43,
006 8/9이 전부 기준 상태 유지(타이틀·모드 선택·Options·스태프롤·캐릭터 선택·
게임플레이·전환·컨티뉴). 이탈은 동영상 재생 구간에서만 발생했다.

**결정: bank 1 = `(448,0)` 전체 페이지(256셀), tpage `0x07`, 뱅크 비트 1개.**
필요 190셀 < 256셀이므로 앞서 검토한 2비트 반쪽 분산은 불필요하다. 판정 JSON은
`work/analysis/font_two_bank_vram_003_placement.json`이 소유한다.

잔여 리스크: 엔딩 동영상→크레딧 전환 구간은 아직 표본이 없다(Options의 스태프롤은
페이지 정상 상태로 통과). 번역 QA 단계의 실제 엔딩 플레이로 닫는다.

도구 주의: 프로브 1회가 실측 약 21초(32KB GDB 판독+스크래치 쓰기/복원)이므로
스케줄 간격을 25초 미만으로 잡으면 세션이 계획보다 훨씬 길어진다.

### 컷신 버퍼 최초 관측 (poc2reg 세션)

PoC 빌드 HITL 회귀 세션(`vram_occupancy_poc2reg`, 44프로브)에서 170초의
애니메이션 컷신 중 **`(448,0)` 페이지의 왼쪽 절반(페이지 로컬 32워드×240행,
즉 `(448,0)`–`(480,240)`)이 컷신 프레임 데이터로 덮이고 종료 후 0으로
재소거**됨을 관측했다(7,671워드, 경계 `[0,0,32,240]`; 프로브 007만 상이,
190초에 원상). PoC 셀 `DE`·`DF`(페이지 우하단 `(504,208)`)는 침범되지 않았다.
세션 001/002의 오프닝 애니메이션에서는 이 페이지가 계속 0이었으므로 이 버퍼는
**인게임 스토리 컷신 전용**으로 보인다. 세션 004(3표본)와 005(59표본)는 컷신
구간에 `(448,0)` 표본이 없어 이를 놓쳤다 — 순간 표본 한계의 실증 사례다.

이 관측이 위 `FONT-TWO-BANK-VRAM-003`의 출발점이 됐다. 후속 무인 감사에서 이
쓰기는 STR 동영상 재생 경로로 밝혀졌고, 재생 후 자산 디렉터리 재업로드로
원상 복구됨이 확인되어 `(448,0)` 전체 페이지 사용으로 결론났다.

builder 패치의 bank 1 tpage 유도(`xori 0x1F`→`0x1E` 고정)는 `(448,0)`=tpage
`0x07`에 맞게 재조립해야 한다(bank bit로 `0x18`을 XOR: `0x1F^0x18=0x07`).
emulator 종료로 세션이 끊겨도 이제 부분 보고서를 기록한다(`SESSION_LOST_PARTIAL`).

## 최종 설계 전환 — HANGUL-ATLAS-001 (2뱅크 VRAM 경로 폐기)

전체 corpus 빌드 단계에서 **두 번째 VRAM 페이지가 불필요함**이 밝혀져 설계를
전환했다. 근거와 구현은 다음과 같다.

### 원리

원본 4bpp 아틀라스는 셀 하나의 **비트플레인 4장**에 같은 글자의 흔들림 프레임
4장을 저장하고, 공용 builder가 전역 카운터로 팔레트 0–3을 선택해 낙서풍 흔들림을
만든다. CLUT을 기록하는 코드는 ARA `0x80043004` **단 한 곳**이며(정적 전수 검색),
움직이는 타이틀 builder를 포함한 모든 텍스트 경로가 이 공용 builder를 호출한다.
따라서 플레인 의미를 우리가 재정의할 수 있다.

**셀당 글자 2개 × 흔들림 2프레임**으로 재배치했다.

| 항목 | 값 |
| --- | --- |
| 플레인 0,1 | 글자 A (bank 0) |
| 플레인 2,3 | 글자 B (bank 1) |
| 팔레트 | `(bank << 1) | ((전역카운터 >> 2) & 1)` |
| 용량 | 255셀 × 2 = **510자** (필요 445자) |
| 아틀라스 위치 | 기존 `(960,256)` 그대로, 크기 동일 |

이로써 두 번째 VRAM 페이지·자산 디렉터리 이전·타이틀 배경 16색 전환이 모두
불필요해졌고, `FONT-TWO-BANK-VRAM-001~003`의 점유 리스크는 배포 의존성에서
제외됐다(감사 기록 자체는 유효한 근거로 보존한다). 흔들림은 2프레임으로 준다.

### decoder와 인코딩

문자열을 우리 인코딩으로 재작성하므로 decoder는 범위 분기 111개 명령에서
**7개 명령**으로 축소됐다.

```
code = 0x8000 + ((bank << 8) | cell)
retval = code - 0x8000          ; 범위 밖이면 blank 셀 0xFF
```

| 항목 | 값 |
| --- | --- |
| 글리프 | 416자 / 208셀 |
| 적용 문자열 | 307행 (전체 324행 중) |
| 수정 raw sector | 35개, 원본 크기 유지 |
| 아틀라스 업로드 | `(960,256)` 판독 2회가 빌드 payload와 바이트 일치 **PASS** |
| 텍스트 렌더 | 타이틀 프롬프트가 `푸시 스타트 버튼`으로 표시, 이동·회전 정상 **PASS** |

판정 JSON은 `work/analysis/hangul_atlas_001_{build,runtime_review}.json`이 소유한다.

### 미해결

원문 바이트 공간을 초과하는 번역 **17행**은 이번 빌드에서 보류했다. 제자리 패치는
문자열을 늘릴 수 없으므로 (a) 번역 축약 또는 (b) 문자열 재배치+포인터 패치 중
하나를 선택해야 한다. 또한 커버리지 감사가 `.notdef` 네모 박스를 유효 글리프로
통과시키던 결함을 이번에 수정했고(39자 오검출), 폴백 배정이 44자로 늘었다.

## 메뉴가 일본어로 남는 이유 — MENU-GRAPHICS-001

한글 패치 후에도 모드 선택·Options 화면이 일본어인 것은 **그 라벨들이 글꼴 텍스트가
아니라 미리 그려진 낱말 비트맵**이기 때문이다. 따라서 324행 문자열 목록에 애초에
없었고, 글꼴·decoder 작업의 영향을 받지 않는다.

근거:

- `モードセレクト`·`オプション`·`デモンストレーション`·`スタッフ`·`キーコンフィグ`·
  `ユーザーフレンドリー`·`サウンド`·`バーサス`·`トレーニング`가 CP932는 물론
  EUC-JP·ISO-2022-JP·UTF-16으로도 ARA/HAGECHO/EXE 어디에도 존재하지 않는다.
- Options 화면에서 캡처한 `(704,256)` 페이지는 셀 단위 글리프가 아니라 **낱말 통짜
  띠**로 렌더된다.
- 그 띠의 64바이트 조각이 HAGECHO `0x55C88`·`0x55F48`과 **바이트 그대로 일치**한다.

저장 형태: HAGECHO block 1(시작 `0x4C800`)의 TIM 이전 영역에 **압축 없이** 놓인
raw 4bpp 비트맵이며 행 stride 88바이트(=176px), 업로드 대상은 `(704,256)`이다.
block 1의 첫 TIM은 `0x5AC7C`이므로 이 데이터는 TIM 헤더 없이 직접 전송된다.

압축이 아니므로 글꼴 아틀라스와 똑같은 Expected Write 방식으로 편집할 수 있다.
다음 단계는 영역 전체 범위 확정 → 낱말 띠 분할 → PNG 검토 → 한국어로 재작화 →
제자리 패치 → `(704,256)` 판독 검증이다. 판정 JSON은
`work/analysis/menu_graphics_001.json`.

## 흔들림 프레임 수정 — FONT-WOBBLE-COUNTER-001

첫 완전판에서 타이틀 프롬프트의 흔들림이 사라져 보인 원인을 규명했다. 팔레트
교대 자체는 정상이었다(카운터 `0x800AECF0`의 비트 2가 실제로 토글함을 GDB로 측정,
`work/analysis/font_wobble_counter_001.json`). 문제는 **흔들림의 성격**이었다.

| | 원본 | 초기 한글판 | 수정본 |
| --- | --- | --- | --- |
| 프레임 성격 | 손으로 다시 그린 변형 | 전체를 1px 평행이동 | 글자별 방향 + 획 굵기 변화 |
| 프레임별 잉크 픽셀 | 27/45/44/35 (제각각) | 82/82 (동일) | 85/76 (다름) |
| 체감 | 획이 출렁임 | 모든 글자가 같이 밀림 → 안 보임 | 글자마다 따로 흔들림 |

수정: 글자마다 문자 해시로 8방향 중 하나를 고르고, 두 프레임의 임계값을 달리해
획 굵기를 바꾼다. 행 단위 워프도 시험했으나 16px 셀에서는 세로획이 끊겨 가독성이
무너져 폐기했다.

**프레임 3장은 불가능하다**: 플레인 4장 ÷ 3프레임 = 셀당 글자 1개 = 최대 255자인데
현재 corpus는 431자가 필요하다. 2프레임(셀당 2자, 510자)이 유일한 해다.

### 배너 TIM 단어 패치 (BANNER-WORDS-001)

block 0 TIM `0x33578`(dest 640,217) 안에 `ゴール`·`ネクストステージ`·`ナウローディング`이
한 이미지로 들어 있다. 열별 잉크 행 범위를 측정해 정확한 박스를 확정했다:
골 `(48,0,24,8)`, 넥스트 스테이지 `(72,0,184,16)`, 나우로딩 `(0,22,167,16)`.
각 박스는 잉크 SHA-256 사전검사 후 그 박스의 **최빈 잉크 인덱스(3)**를 그대로 써서
제자리 재작화한다(`max()`를 쓰면 안티에일리어싱 잔여 인덱스가 잡혀 색이 튄다).

`ゴール` 박스는 24×8이라 RiaSans-ExtraBold가 뭉개져 **Galmuri9 픽셀 폰트**로
전환했다(높이 12px 미만이면 자동). 설정은 `workspace/config/banner_words.json`,
결과는 빌드 `323B1044...`(섹터 59).

### 배경 파괴 회귀 수정 + Bold 전환 (빌드 4258792586029432)

사용자 플레이에서 **로딩·넥스트 스테이지 배경이 사라지는 회귀**가 보고됐다. 원인은
배너 단어 패치가 박스 전체를 0으로 밀어 텍스트가 아닌 요소까지 지운 것으로,
원본 대비 인덱스 4·14·15의 **212픽셀**이 파괴됐음을 픽셀 diff로 확인했다. 이 인덱스는
게임이 같은 텍스처에서 그리는 배경판·장식이다.

수정: 각 박스의 **자기 텍스트 잉크와 같은 인덱스만** 0으로 지우고, 새 글리프는
원본이 배경(0) 또는 그 잉크였던 자리에만 쓴다. 재빌드 후 비텍스트 픽셀 변경 **0**을
검증했다.

함께 반영: 폰트를 RiaSans-ExtraBold → **RiaSans-Bold**로 교체(16px에서 획이 붙음),
`モノラル` 번역을 모노럴→**모노**, `ロード`(0x50518, 64px)를 찾아 **로드**로 추가해
라벨 43개가 됐다.

주의: `texture_session_004`는 세션이 중단돼 DuckStation textures 루트에서 회수한
탓에 **다른 게임(텐추 SLPS-01762) 덤프가 섞여 있다**. 디스크 대조로 검증된 매칭만
신뢰하며, 이후 세션은 SLPM-86272 하위 폴더만 읽어야 한다.

### 전략 전환: LoadImage 추적 (LOADIMAGE-TRACE-001)

텍스처 덤프를 뜬 뒤 디스크와 마스크 매칭하는 방식은 검색 영역과 임계값이 모두
추측이라 세션을 거듭해도 수확이 급감했다(17→31→38→42→47, 매번 몇 개씩). 그래서
**게임에게 직접 묻는 방식**으로 바꿨다.

ARA `0x8008C2D8`이 `LoadImage(RECT *a0, void *a1)`다(GP0 `A0h` 패킷을 쓰는
`0x8008C3DC`에서 역추적). 여기에 GDB 중단점을 걸면 게임이 그래픽을 올릴 때마다
**목적지 RECT와 소스 RAM 주소**를 그대로 얻는다(`workspace/scripts/trace_loadimage.py`).

RAM→디스크 변환 검증: 글꼴 아틀라스 업로드의 소스 `0x80160898`이 블록 0 기준
`0x34BB8`로 나와 TIM payload 오프셋과 **오차 0**이었다. 라벨이 든 블록은 로드
주소가 달라, 알려진 라벨 폭과 추적 폭을 대조해 델타 `0x800DF4D0`을 60건 일치로
확정했다.

성과: 여러 세션 동안 못 찾던 `クレジット`·`スペシャル`·`ヒョウジ`를 한 번에
확정했다(각 `0x50998`·`0x51618`·`0x52518`). 라벨 총 50개.

도구 주의: 세션을 중간에 끊으면 보고서가 안 써져 플레이가 통째로 날아가므로
20초마다 중간 저장하도록 고쳤다(`--flush-every`).

### 지문 기반 추적으로 전환 (LOADIMAGE-TRACE 개선)

소스 주소만 기록한 1차 추적은 RAM→디스크 변환에 **블록별 로드 주소를 추측**해야
했고, 델타 하나(`0x800DF4D0`)만 가정한 탓에 다른 블록의 그래픽이 조용히 걸러졌다.
사용자가 해당 화면을 모두 거쳤는데도 `팀`·`카라`·대형 인게임 텍스트가 안 잡힌 원인이
이것이다.

수정: 업로드마다 **소스 픽셀 96바이트 지문**을 함께 기록하고, 디스크에서 그 바이트열을
직접 찾는다(`--signature-bytes`). 추측이 사라지고 블록 로드 주소는 역산으로 나온다.
부팅 75초 검증에서 166건이 유일 매칭됐고 **로드 주소 6종이 자동 발견**됐다
(`0x7F5BFCE0`·`0x800DF4D0`·`0x8012BCE0`·`0x7FF104D0` 등).

세션 003(HITL) 결과: 업로드 2,204건 중 847건을 디스크에서 확정했다. 미해결 91건은
대부분 **이미 한글로 패치한 라벨**(원본 파일과 다르니 당연)이었고, 패치 빌드까지
대조 대상에 넣어 스태프롤의 두 그래픽을 새로 확정했다:
`トレジャー`(`0x21E1EC`, 88px)·`ラクガキショータイム`(`0x21BD6C`, 208px).
이로써 라벨 **52개**, 빌드 `39C43B92`(섹터 66).
