다음 게이트 1번(후보 두 번째 글꼴 뱅크 VRAM 페이지 `(704,256)`–`(768,512)`의

1. **도구 제약 확인**: 이 DuckStation 빌드(0.1-11636)는 GPU 디버그 로그 포맷
   문자열이 실행 파일에 없어 로그 기반 감사가 불가능하고(과거
   `gpu_upload_coordinates.json`도 실제로는 업로드 0건), GDB 서버는 레지스터 쓰기
   `G`/`P`/`p`를 지원하지 않는다(라이브 테스트, 빈 응답). `m`/`M`/`Z0`/`s`/`c`는
   동작한다.
2. **새 감사 기법**: 레지스터·pc 쓰기가 전혀 없는 in-line pc hijack + GP0 `C0h`
   판독 스텁(`workspace/scripts/capture_vram_occupancy.py`). 멈춘 지점 `F`의 2개
   명령을 `j 0x80017000`으로 치환하면, 스크래치의 스텁이 레지스터/SR을 스스로

   복원한다. 다중 사각형 라운드로빈(`--rect "a;b;c"`)과 emulator 소실 시 부분

## 컷신·상주 모델 판정 (FONT-TWO-BANK-VRAM-003)

PoC-002 회귀 세션에서 발견한 `(448,0)` 컷신 쓰기를 추적한 결과, 상주 조건 자체를
수정했다.

1. **컷신 = STR 동영상 7편**: `MOVIE/OPEN.STR`, `GOOD/BAD.STR`, `NE_A~D.STR`.
   전 파일 프레임이 320×240임을 디스크에서 정적 확인. 캐릭터별 사망 컷신이
   동일했던 것은 같은 파일 재생이기 때문이며, 엔딩 6편은 오프닝과 같은 재생
   경로다 → **어트랙트 오프닝 관측으로 엔딩까지 판정 가능**(치트 불필요).
2. **영구 안전 페이지는 없다**: 무인 세션 `007attract`에서 동영상이 `(448,0)`을
   초반 32워드, 후반 페이지 전체까지 덮었고, `008attract`(72표본)에서
   `(512,256)`은 256셀 중 165셀이 오염됐다.
3. **그러나 복원된다**: 동영상 종료 후 `(448,0)`이 PoC 기준 해시로 바이트 복귀 —
   이전된 자산 디렉터리가 장면 로드에서 미니 TIM을 재업로드한다.
4. **수정된 상주 조건**: "절대 안 쓰이는 페이지"가 아니라 "한국어 텍스트가 있는
   동안 안 쓰이고 텍스트 복귀 전에 복원되는 페이지". 전체 화면 동영상 중에는
   게임 텍스트가 그려지지 않는다.
5. **결정: bank 1 = `(448,0)` 전체 256셀, tpage `0x07`, 뱅크 비트 1개.** 필요
   190셀 < 256셀이므로 2비트 분산 설계는 불필요. 대화형 플레이 근거는 세션 005
   59표본·006b 36표본·poc2reg 42/43·006 8/9 전부 기준 상태 유지.

부수 확인: 공개 치트는 스테이지별 플레이어 무한 체력 4종뿐이고 원히트킬은 없다.
자체 HP 매핑 세션(`ENTITY-HP-MAP-001`)에서 공개 코드 주소가 실제 HP를 담지 않음을
확인했으나(최대값 `0x091D` 부재), 위 1번으로 치트 경로 자체가 불필요해졌다.

도구 주의: 프로브 1회 실측 약 21초이므로 스케줄 간격은 25초 이상으로 잡는다.
세션 008attract는 이 때문에 사용자가 72/110에서 중단했고, 그 시점에 이미 판정에
충분했다.

## 전체 corpus 빌드와 설계 전환 (HANGUL-ATLAS-001)

전체 atlas 제작 단계에서 **두 번째 VRAM 페이지 자체가 불필요**함이 밝혀져 설계를
전환했다. 2뱅크 VRAM 감사 기록(`VRAM-001~003`)은 근거로 보존하되 배포 의존성에서는
제외됐다.

1. **원리**: 원본 4bpp 셀은 비트플레인 4장에 흔들림 프레임 4장을 담고 공용 builder가
   팔레트 0–3으로 선택한다. CLUT 기록 코드는 ARA `0x80043004` 단 한 곳(정적 전수
   검색)이고 모든 텍스트 경로가 이 builder를 호출하므로 플레인 의미를 재정의할 수
   있다. **셀당 글자 2개 × 흔들림 2프레임**으로 바꿔 용량을 255→510자로 늘렸다.
   팔레트 = `(bank << 1) | ((전역카운터 >> 2) & 1)`.
2. **효과**: 두 번째 VRAM 페이지, 자산 디렉터리 이전, 타이틀 배경 16색 전환이 모두
   불필요. 아틀라스는 기존 `(960,256)`을 같은 크기로 교체한다.
3. **decoder 축소**: 문자열을 자체 인코딩(`code = 0x8000 + (bank<<8|cell)`)으로
   재작성하므로 decoder는 범위 분기 111개 명령 → **7개 명령**(`retval = code -
   0x8000`, 범위 밖 blank 폴백).
4. **빌드(완전판)**: 글리프 431자/216셀(255셀 중 39셀 여유), 문자열 **324/324행
   전부 적용**, 수정 raw sector 35개, 원본 크기 유지. 산출물
   `build/hangul_atlas_001/`, BIN SHA-256 `052CA9B4...3D40EF`.
5. **런타임 PASS**: `(960,256)` 판독이 빌드 payload(`6A2DE315...89E786`)와 바이트
   일치, 타이틀 프롬프트가 `푸시 스타트 버튼`으로 표시되고 이동·회전 정상,
   부팅·어트랙트 회귀 없음. (두 번째 프로브는 스텁 미실행으로 `0xAA` 초기값이

   새 decoder는 미번역 문자열을 빈칸으로 만들므로, **화면의 빈칸이 곧 미번역 탐지기**다.

### 도구 전환 — 덤프 매칭에서 LoadImage 추적으로

텍스처 덤프를 디스크와 마스크 매칭하는 방식은 검색 영역·임계값이 모두 추측이라
다섯 세션에 걸쳐 수확이 급감했다(17→31→38→42→47). `LoadImage(RECT*, src*)`
(ARA `0x8008C2D8`)에 중단점을 걸어 **게임이 목적지와 소스를 직접 알려주도록** 바꿨다.

1차 추적은 소스 주소만 기록해 RAM→디스크 변환에 블록별 로드 주소를 추측해야 했고,
델타 하나만 가정한 탓에 다른 블록 그래픽이 조용히 걸러졌다(사용자가 화면을 다
거쳤는데도 안 잡힌 원인). **업로드마다 픽셀 96바이트 지문을 기록**하도록 고쳐
디스크에서 직접 찾게 하니 추측이 사라지고 로드 주소 6종이 자동으로 나왔다.
세션 003에서 업로드 2,204건 중 847건을 확정했다.

매칭 시 **패치된 빌드도 대조 대상에 넣어야 한다** — 이미 한글화한 자산은 원본
파일과 더는 일치하지 않아 "미해결"로 오분류된다(91건 중 대부분이 이 경우였다).
